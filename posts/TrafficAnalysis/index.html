追踪HTTP流与追踪TCP流

【有时候数据藏在 GET 请求头结束后的裸 TCP payload 里，HTTP 层不一定认，但 TCP 层一定能看到】

例子：[玄武杯 2025] misc1【在GET请求体中隐藏密文；HTTP追踪流就解析不到】

数据 不是一个规范的 HTTP 请求体时，Wireshark 的 HTTP 解析器不会把它当成 HTTP 内容展示；但 TCP 流追踪只按字节流展示，所以能看到。

关键点是：

HTTP 里请求头和请求体靠空行 \r\n\r\n 分隔。但这个请求有两个异常：

  1. 它是 GET 请求
    GET 理论上可以带 body，但非常少见，很多工具和解析器会弱化甚至忽略 GET body。
  2. 没有 Content-Length 或 Transfer-Encoding: chunked
    HTTP 解析器需要这些字段判断 body 长度。没有长度声明时，Wireshark 不知道空行后的字节是否属于 HTTP body，于是不会把它解析成 HTTP payload。

所以：

  • Follow HTTP Stream：按 HTTP 协议语义重组，只展示它认为属于 HTTP 消息的内容。那段密文没有被 HTTP 层认定为合法 body，因此可能被漏掉。
  • Follow TCP Stream：不管协议语义，只把同一个 TCP 连接里的应用层字节原样拼出来。空行后的隐藏密文就会显示。

TLS流量分析

TLS（Transport Layer Security）是一种安全协议，用于在计算机网络上实现加密通信

TLS 使用密钥交换算法来安全地生成一个共享的会话密钥，这个会话密钥将用于本次通信会话的加密和解密

常见的密钥交换算法包括 RSA、DH、ECDH 等

【这类题目的核心就是找到】

  • Wireshark解密TLS流量的前提是获取以下任一要素：

    • 服务器私钥 (RSA密钥)

    • 会话密钥日志 (SSLKEYLOGFILE)

    • 预共享密钥 (PSK)

  • 常用的TLS版本及对应解密文件：

    • TLS 1.2 + RSA key exchange（TLS_RSA_WITH_...）：
      服务器私钥可以用来解出握手里的 pre-master secret，进而派生出会话对称密钥，所以 Wireshark 才能用私钥解密流量。
    • TLS 1.2 + (EC)DHE（ECDHE_... / DHE_...）或 TLS 1.3：
      服务器私钥主要用于签名认证（证明“我真是这个服务器”），不能直接解密会话内容（每一个会话都会有自己的密钥）；想解密通常要用 key log（SSLKEYLOGFILE 那种 traffic secret）。

USB流量包简介及分析过滤方法

  • 这里顺便介绍一下 USB 设备的相关流量含义

  • usb.src 的格式在Wireshark中显示为 总线.设备地址.端点 的格式；过滤具体的设备可以用 usb.device_address == 9 这样的语句进行

    • 比如 2.9.1：
      • 2 = bus id（总线）
      • 9 = device address（设备地址）
      • 1 = endpoint number（端点号）
      • 【也就是说不同的设备是用设备地址区分的，最后一位不同代表同一个设备的不同端点号而已】

  • 一般 USB 设备刚接入时，主机会通过 端点0（EP0，控制传输） 读取设备/配置等描述符并完成枚举与配置（例如分配地址、选择配置、了解接口与端点）。配置完成后，设备才会在描述符声明的端点上（如 2.9.1 的中断 IN 端点）进行正常数据通信。以 2.9.0 为例，它对应设备地址 9 的 EP0，专门用来做这些初始化控制请求。usb.device_address == xxx

  • 查看设备类型一般使用配置描述符的接口信息描述 GET DESCRIPTOR: Response CONFIGURATION → Configuration Descriptor → Interface Descriptor

【wMaxPacketSize: 8 → 并且最大包长 8 字节 → 就是后面的 HID Data: 8 bytes】

【在开头的设备描述符相关包中只能看到部分设备类型（不是一个单一类型的设备就看不到，Class会被设置成 0x00 ），所以实践里还是看配置描述符/接口描述符更可靠（就是第二组配置描述符的回显包）】

虽然但是，这个还是有用的，比如说查看有哪些USB设备【后面发现实则 统计 → 流量图里也能看】 → 过滤方式就是 usb.setup.bRequest == 6

usb.setup.bRequest == 6 过滤的是 USB 控制传输（Control Transfer）里的请求码= 6 的 SETUP 包。

【在 USB 里，控制传输一开始都会有一个 Setup Packet，里面有个字段叫 bRequest； bRequest = 0x06 的标准含义是：GET_DESCRIPTOR（获取描述符）】

  • 其中设备地址为1的一般都是根集线器 Root Hub(0x09) →
    • 它在 主机端（电脑/手机作为主机），属于 USB 主控制器内部的集线器功能。
    • 硬件上它一般不是一个能拔插的外设，而是控制器的一部分。
    • 软件/协议上系统把它抽象成一个 USB Hub 设备，这样就能用同样的 USBHUB 请求去管端口：供电、挂起/恢复、检测插拔、查询端口状态（抓到的 GET_STATUS [Port X] 就是它在干活）

严谨点可以带上地址分配的流量 usb.setup.bRequest == 5 || usb.setup.bRequest == 6

【bRequest==5：SET_ADDRESS（主机给新设备分配 device address）】

Modbus协议

Modbus 是一种很老但现在还大量存在的工业通信协议，常见于 PLC、HMI、变频器、电表、RTU、IO 模块之间通信。

它的核心特点很简单：

  • 请求-响应模型【一个设备发请求，另一个设备回响应】
  • 传统上是 主从（Master/Slave），现在也常说 Client/Server
  • 协议本身几乎没有认证和加密【明文传输】

流量分析时，最常见的是两类：

  • Modbus RTU：跑在串口链路上，二进制格式
  • Modbus TCP：跑在 TCP 上，默认端口 502

ICMP协议

ICMP（Internet Control Message Protocol，因特网控制报文协议）是TCP/IP协议族中的一个重要组成部分，它主要用于在网络设备和路由器之间传递控制消息。这些控制消息包括网络是否通畅、主机是否可达、路由是否可用等信息。虽然ICMP消息不传输用户数据，但它对用户数据的传输起着至关重要的作用。

TTL隐藏信息

这里的 TTL 字段指的是 IP 头部（IPv4）里的 Time To Live（生存时间），不是 ICMP 自己的字段。用于限制一个 IP 包在网络里最多能经过多少跳（路由器）。每经过一个三层设备（路由器/三层交换），TTL 就减 1；减到 0 就丢包并返回 ICMP Time Exceeded，防止路由环路让包永远转圈。

正常情况下同一主机发出的同类型流量 TTL 应该很稳定（比如一直 64/128/255 之一）

  • 这里也是第一次见 WinRM 的流量，因此记录一下原理

  • 先是几个有关 WinRM 的名词：

    • 简单来说就是通过 HTTP/HTTPS 承载的远程管理机制，可以执行管理操作、命令调用、PowerShell Remoting、WMI 访问等；它不是像 RDP 那样的图形化远控程序（个人理解是类似 ssh 的操作），而是更偏管理接口/管理通道。微软文档明确说 WinRM 是通过 SOAP-based WS-Management 建立远程会话，而不是走 DCOM。【微软默认的 WinRM 监听端口就是 HTTP 5985 和 HTTPS 5986】
    • 这里就会出现一个问题，那就是SOAP消息封装本身是不加密的，如果是用HTTPS协议的话就由传输层直接加密；而HTTP却是明文传输的协议 → 因此这里就需要由WinRM在认证后再来负责加密：也就是HTTP + WinRM 认证上下文（ NTLM 或 Kerberos 在认证阶段建立安全上下文，再用这个上下文派生/协商出的会话密钥去保护后续 WinRM 消息 ）【这个题目选择的是NTLM】

  • 然后是WinRM的具体通信流程：【这个题目成功建立了三次成功的NTLM握手，以第一次握手为例】

    • 第一步：1272 → 客户端发起 WinRM 请求，同时发 NTLM 协商（NTLM Type 1）
    • 第二步：1273 → 服务端拒绝直接访问，返回 401 和 Challenge（NTLM Type 2）
    • 第三步：1276 → 客户端提交认证结果，真正证明身份（NTLMSSP Type3）
    • 第四步：1279 → 服务端回 200，认证通过
    • 1279后面的就是加密通信的内容了
    • PS：这个TYPE就是固定的字段，比如这里就是1(0x00000001)：【ntlmssp.messagetype】

IPMI通信流量

  • IPMI（Intelligent Platform Management Interface，智能平台管理接口）是一套带外管理标准，主要用于服务器硬件监控与远程运维。它的核心特点是：就算操作系统死机、机器关机但主板仍有待机电，管理员也可能通过 IPMI 管理服务器。IPMI 里最关键的东西是 BMC（Baseboard Management Controller，基板管理控制器）：它是主板上的一个独立小控制器，相当于服务器里的另一个小电脑。【IPMI 相当于依托独立管理硬件（BMC）实现的一套远程服务器管理协议】

  • IPMI 属于带外管理（Out-of-Band Management）。意思是管理通道不依赖业务操作系统和普通业务网卡。【这和普通 SSH、RDP 这种**带内管理（In-Band）**不同。】

  • RMCP+ 是 IPMI 2.0 远程管理常用承载协议

  • 虽然通信过程中，有认证，有加密，有完整性保护，但此协议本身设计的并不足够安全，导致在捕获到合法用户的认证流量后，可对其登录口令进行离线破解，最终解密其通信流量。

这个字段的取值解释要去看 Table 13-19, Confidentiality Algorithm Numbers。

  • 这里以题目中的一个Request请求为例

    • (1) 前 8 字节

      • 00 = Message Tag
      • 00 = Requested Maximum Privilege Level
        0h 的意思不是“无权限”，而是：让 BMC 从符合提案的算法组合里，选一个最高可匹配的 privilege level。
      • 00 00 = reserved
      • a4 a3 a2 a0 = Remote Console Session ID（控制端自己选的一个临时标识）

      (2) Authentication Payload

      按 Table 13-9 拆：

      • byte1 = 00 → authentication algorithm payload
      • byte2:3 = 0000
      • byte4 = 08 → 这个 payload 总长度 8 字节
      • byte5 = 01 → Authentication Algorithm = 01h
      • byte6:8 = 000000

      而 Table 13-17 里定义：

      • 00h = RAKP-none
      • 01h = RAKP-HMAC-SHA1
      • 02h = RAKP-HMAC-MD5
      • 03h = RAKP-HMAC-SHA256

      所以这一段表示：

      认证握手算法 = RAKP-HMAC-SHA1。

      (3) Integrity Payload

      按 Table 13-9 拆：

      • byte1 = 01 → integrity algorithm payload
      • byte4 = 08
      • byte5 = 01 → Integrity Algorithm = 01h

      而 Table 13-18 里定义：

      • 00h = none
      • 01h = HMAC-SHA1-96
      • 02h = HMAC-MD5-128
      • 03h = MD5-128
      • 04h = HMAC-SHA256-128

      所以这一段表示：

      完整性保护算法 = HMAC-SHA1-96。

      (4) Confidentiality Payload

      按 Table 13-9 拆：

      • byte1 = 02 → confidentiality algorithm payload
      • byte4 = 08
      • byte5 = 01 → Confidentiality Algorithm = 01h

      而 Table 13-19 里定义：

      • 00h = none
      • 01h = AES-CBC-128
      • 02h = xRC4-128
      • 03h = xRC4-40

      所以这一段表示：

      保密/加密算法 = AES-CBC-128。

      总结来说

      这帧 Request 不是在展示已经加密后的 payload，而是在提议后续 session 使用哪组算法。这帧提议的是：

      • Authentication = 01h → RAKP-HMAC-SHA1
      • Integrity = 01h → HMAC-SHA1-96
      • Confidentiality = 01h → AES-CBC-128

      按规范，真正最终生效的是 Open Session Response 里 BMC 选中的那组单个 payload。但这个 Request 每类只给了一个候选值，所以如果对方接受，Response 通常就会回同一组 01 / 01 / 01

  • 再以题目中的对应Response响应说明一下字段含义

    • 后面 24 字节是 3 个 最终选中的算法 payload：

      1）Authentication Payload

      • byte1 = 00：这是 Authentication payload
      • byte4 = 08：payload 总长度 8 字节
      • byte5 = 01：Authentication Algorithm = 01h

      规范的算法表里，01h = RAKP-HMAC-SHA1。

      2）Integrity Payload

      • byte1 = 01：这是 Integrity payload
      • byte4 = 08
      • byte5 = 01：Integrity Algorithm = 01h

      规范表里，01h = HMAC-SHA1-96。

      3）Confidentiality Payload

      • byte1 = 02：这是 Confidentiality payload
      • byte4 = 08
      • byte5 = 01：Confidentiality Algorithm = 01h

      规范表里，01h = AES-CBC-128。

      所以，这个 Response 的核心结论就是：

      BMC 最终接受并选定了这组算法：

      • Authentication = 01h → RAKP-HMAC-SHA1
      • Integrity = 01h → HMAC-SHA1-96
      • Confidentiality = 01h → AES-CBC-128
        而且把这次会话的最大权限定为了 Administrator
